# docs-sync: mirror Helm chart changes into camunda-docs

Camunda maintains several chart lines at once (`charts/camunda-platform-<minor>/`),
and end users read about them on docs.camunda.io. When a chart PR changes what
users configure or how the chart behaves, the matching docs version must change
too, or SREs follow instructions that no longer work.

The skill runs in two modes:

- **analyze**: work out the docs impact and write the PR comment. CI runs this on
  every Helm PR push (see `assets/docs-sync.yaml`); engineers can run it locally
  with `/docs-sync analyze`. It never edits the docs repo.
- **apply** (default for `/docs-sync`): run locally by the engineer. Does the
  analysis (or reuses CI's), shows the plan, and after confirmation opens or
  updates a **draft** camunda-docs PR. CI marks it ready when the Helm PR merges.

## Step 1: Identify the PR and get both repos ready

1. Find the Helm PR: the argument if given, otherwise `gh pr view --json number,title,body,baseRefName,headRefOid,url`
   on the current branch. In CI the PR number and SHAs are given in the prompt.
2. Locate a camunda-docs checkout. Use `$CAMUNDA_DOCS_PATH`, else `../camunda-docs`,
   else ask before cloning (it is large; `gh repo clone camunda/camunda-docs -- --filter=blob:none`
   keeps it manageable). Bring `main` up to date before branching. In CI the
   workflow has already checked it out at `./camunda-docs`.
3. Read the docs repo's own agent instructions before planning any edit:
   `AGENTS.md`, `.github/instructions/content.instructions.md`, and
   `.github/instructions/repo.instructions.md`. They define style, terminology,
   versioning, and commit rules. Where they conflict with this skill, they win
   for anything inside camunda-docs.

## Step 2: Collect the facts

Run the diff script from the Helm repo root:

```bash
python3 .claude/skills/docs-sync/scripts/chart_diff.py \
  --base origin/<baseRefName> --head HEAD --docs-repo <camunda-docs path>
```

It prints JSON per chart minor: values added, removed, possibly renamed, default
changes, description changes, newly deprecated keys, image bumps, other changed
files, whether templates or schema changed, breaking signals from commit
messages (`type!:` or `BREAKING CHANGE`), and the docs folder each minor maps to.

The script reports facts, not conclusions. Also read:

- The PR title and description. Engineers often explain intent, migration
  steps, and whether output changes there.
- The actual diff for anything flagged: `git diff <merge_base> HEAD -- charts/camunda-platform-<minor>/templates`
  and the golden files under `test/` show whether rendered manifests changed.
- The chart's `README.md` diff: the hand-written notes above the autogenerated
  parameters table often carry the user-facing explanation.

## Step 3: Decide the docs impact

For each chart minor, classify every change. The goal is to describe changes
from the user's point of view: what they must set, stop setting, or expect
differently after upgrading.

| Kind | Typical signal | Docs action |
|---|---|---|
| New value or feature | `added`, `feat:` commit, new template | Document on the topic page; release-notes entry if it ships in an unreleased tag |
| Renamed or removed value | `possible_renames`, `removed`, schema rejects key | Upgrade guide subsection with before/after YAML; announcements entry; fix every page that still shows the old key |
| Changed default | `default_changed` | Update pages that state the default; if behavior changes for existing installs, announcements entry and upgrade guide note |
| Changed behavior, no values change | template diff changes rendered output | Update the page explaining that behavior; announcements if action is needed |
| Deprecation | `newly_deprecated`, description mentions removal target | Announcements entry with the replacement and removal version; note on the topic page |
| Breaking | `breaking_signals`, or any of the above that makes an upgrade fail or change silently | Always an announcements entry, even if no other page changes |

`references/docs-map.md` lists where each chart area is documented, the upgrade
guide and release-notes conventions, and what never needs docs (image bumps,
tests, wording-only description fixes). Read it now.

Then search each target version folder for the affected keys to find pages
that mention them. Pages that show an old default or a removed key are the
most important to catch: they are where users get misled.

### Version mapping

Mirror automatically, using `docs_target` from the script:

- Newest chart line not yet in `versions.json` → `docs/` (Next).
- Chart lines listed in `versions.json` → `versioned_docs/version-<minor>/`.
- Older chart lines (no docs folder) → skip, and list them as skipped so
  nobody wonders whether they were forgotten.

A PR that touches several chart lines can differ per line (one line gets a
feature, another only a backported fix). Decide per minor; don't copy the Next
edit blindly into older folders, because page paths, defaults, and surrounding
text can differ between versions.

### Analyze mode ends here

Write the comment body exactly as described in `references/pr-comment.md` and
stop. In CI, write it to the path given in the prompt; the workflow posts it.
Locally, update the comment with `gh` (find it by the `docs-sync:comment`
marker, keep any `docs-pr` and `synced-head` markers).

## Step 4 (apply): confirm the plan

Show the engineer a short plan before touching the docs repo: per docs folder,
the files to edit and a one-line summary of each edit, plus skipped chart lines
and open questions (for example, which release tag a feature ships in, or a
missing upgrade guide). Ask them to confirm or adjust. They know the release
schedule and intent; the diff does not.

If the analysis finds no docs impact, say so with the reason, update the PR
comment, and stop.

## Step 5 (apply): edit, commit, open or update the draft PR

1. **Branch.** Look for an existing docs PR: the `docs-sync:docs-pr` marker in
   the Helm PR comment, else `gh pr list --repo camunda/camunda-docs --head helm-<N>-<slug> --state open`.
   If one exists, check out its branch and update it; otherwise create
   `helm-<N>-<short-slug>` from up-to-date `main`.
2. **Edit** each target version folder. Match the voice and structure of the
   surrounding page, follow `content.instructions.md`, show values in YAML
   blocks the way neighboring sections do, and link to the Helm PR nowhere in
   user-facing text (users don't need it; the PR description carries it).
3. **Release announcements and notes** for each affected minor, per the rules in
   `references/docs-map.md`.
4. **Validate** lightly, as the docs AGENTS.md asks: run Prettier on the changed
   files (`npx prettier --write <files>`). Run the scoped build only when you
   added, moved, or removed pages or changed links or sidebars.
5. **Commit** with the docs repo's commit convention (see `repo.instructions.md`),
   which requires a 72–120 character header in present tense, for example
   `docs(self-managed): Document that the Optimize Elasticsearch host has no Helm default in 8.10 and 8.11`.
6. **Open the PR** by following the docs repo's own `.claude/skills/create-pr/SKILL.md`,
   with these specifics:
   - Open it as a **draft** (`gh pr create --draft`). It goes ready when the
     Helm PR merges, so docs never describe an unmerged chart.
   - In the `## Description`, link the Helm PR and list per version what changed.
   - In "When should this change go live?", tick the "specific schedule" box
     (draft PR) and explain it releases with the Helm chart.
   - Tick the `/docs` and/or `/versioned_docs` checklist items that apply.
   When updating an existing PR, push to its branch and edit only the
   `## Description` section if the change list grew.
7. **Cross-link** on the Helm PR: update the docs-sync comment so it carries
   `<!-- docs-sync:docs-pr=<url> -->` and `<!-- docs-sync:synced-head=<helm head sha> -->`,
   and switch its last line to the "in sync" status.

Finish by giving the engineer the docs PR link, the files changed per version,
and anything left for them (open questions, missing upgrade guide, versions
skipped).

## Things that go wrong

- **Assuming a page path exists in every version.** Check each folder; if a page
  is missing in an older version, find its equivalent by searching for the
  topic, or report it.
- **Documenting internal details.** Template helper names, golden files and CI
  scenarios mean nothing to users. Describe the values they set and the
  behavior they see.
- **Over-documenting.** Not every new `@param` needs prose; many are covered by
  the Artifact Hub parameters table that `chart-parameters.md` links to. Write
  prose when the value is something users must decide about, when it changes
  behavior, or when a page already discusses that area.
- **Touching versions the PR didn't touch.** Only edit docs folders for chart
  lines the PR changed. The docs repo treats backports as an author decision,
  and here the Helm PR is that decision.
